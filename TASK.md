## 1. Цель работы

Создать простой инструмент на Python, который:

1. Получает данные об угрозах из логов и/или API.
2. Выявляет потенциальные угрозы: уязвимости, подозрительный сетевой трафик и т. п.
3. Реагирует на найденные угрозы.
4. Сохраняет результаты анализа в виде отчёта и графика.

Сложную инфраструктуру разворачивать не требуется: важны понятная логика и работающий код.

| Дополнительная библиотека | `seaborn` — по желанию |

```bash
pip install requests pandas matplotlib seaborn
```

## 3. Источники данных — выбрать минимум два

1. **VirusTotal API** — проверка IP-адресов, файлов или доменов.
2. **Vulners API** — поиск информации об уязвимостях.
3. **Suricata logs** — журналы событий сетевой безопасности.

Можно использовать любую комбинацию из двух или все три источника. Допускается заранее создать папку с журналами и подготовить примеры данных.

**Важно:** не нужно использовать настоящие вирусы или вредоносные файлы. Имитация действий допускается.

## 4. Этапы выполнения

### Этап 1. Сбор данных

- [ ] Выбрать не менее двух источников из списка выше.
- [ ] Обеспечить доступ к выбранным API и/или журналам.
- [ ] Подготовить необходимые тестовые файлы и входные данные.
- [ ] Написать код для чтения логов или выполнения API-запросов.

**Ожидаемый результат:** скрипт способен получить или прочитать исходные данные как минимум из двух источников.

### Этап 2. Анализ данных

- [ ] Обработать полученные ответы API или записи логов.
- [ ] Использовать `pandas`, `json`, `requests` по назначению для работы с данными и API.
- [ ] Реализовать выявление потенциальных угроз.
- [ ] Выводить понятную информацию о найденных угрозах.

Примеры признаков угроз из задания:

- опасные уязвимости с высоким показателем CVSS;
- подозрительные IP-адреса;
- подозрительный трафик (например, частые DNS-запросы).

**Ожидаемый результат:** по обработанным данным можно определить, какие события признаны подозрительными и почему.

### Этап 3. Реагирование на угрозы

Если угроза найдена, реализовать простую реакцию, например:

- сообщение в консоль об обнаруженной угрозе;
- имитацию блокировки IP-адреса;
- уведомление в Telegram или по электронной почте.

**Реальная блокировка не требуется.** По тексту задания достаточно имитации с сообщением в консоль. Отправка сообщений в Telegram или email — возможный, но не обязательный вариант.

**Ожидаемый результат:** после обнаружения угрозы скрипт выполняет заметное и понятное действие.

### Этап 4. Отчёт и визуализация

- [ ] Сформировать отчёт по результатам анализа.
- [ ] Сохранить его в `.json` или `.csv`.
- [ ] Построить минимум один график с помощью `matplotlib` (допускается `seaborn`).
- [ ] Сохранить график в `.png`.

Примеры графиков из задания:

- топ-5 IP-адресов;
- распределение CVSS-баллов.

**Ожидаемый результат:** после запуска программы формируются файлы отчёта и графика.

## 7. Рекомендация по реализации (не дополнительное требование Smart LMS)

Для простого, воспроизводимого решения можно выбрать **логи Suricata + Vulners API** или **логи Suricata + VirusTotal API**. Тогда один источник — локальный файл, другой — внешний API. Конкретную пару следует выбрать с учётом доступности API и тестовых данных.

Пример возможной структуры проекта:

```text
python-threat-monitor/
├── TASK.md                  # Это техническое задание
├── README.md                # Краткое описание, запуск, источники данных
├── requirements.txt         # Сторонние зависимости
├── .gitignore               # Исключения для Git
├── main.py                  # Точка входа
├── data/
│   └── example_events.json  # Небольшой пример входных логов
├── reports/
│   ├── threats.json         # Итоговый отчёт
│   └── threats_chart.png    # Итоговый график
└── .env.example             # Шаблон имён переменных окружения (если нужны API-ключи)
```

Это **пример**, а не обязательный перечень файлов. Вместо отдельных модулей допустим один `.py`-файл, если его удобно читать и запускать.

Предлагаемый процесс исполнения:

1. Загрузить два источника данных (при ошибке API сообщать об ошибке понятно, не скрывая её).
2. Привести записи к единому удобному виду.
3. Применить объяснимые правила обнаружения (например, порог CVSS или количество подозрительных DNS-запросов).
4. Вывести предупреждение или имитацию блокировки при срабатывании правила.
5. Записать результаты анализа в JSON/CSV.
6. Построить и сохранить PNG-график.

### Рекомендации по качеству и безопасности

- Не хранить настоящие API-ключи в коде или публичном GitHub; использовать переменные окружения. Пример настроек без секретов можно положить в `.env.example`.
- Для демонстрации на занятии подготовить небольшой воспроизводимый пример данных без вредоносных файлов.
- Указывать в `README.md`, какие источники используются, как установить зависимости и как запустить программу.
- Пояснять правила распознавания угроз: почему событие считается опасным и какая реакция применяется.
- Проверить сценарий отсутствия угроз: программа должна завершаться корректно и создавать понятный отчёт/график.
- Проверить, что результат получен из двух источников, а не только из одного тестового файла.
